### PAY.JP v2 Checkout Session への移行
| 項目 | 決定内容 | 理由 |
|---|---|---|
| 決済方式 | v1（pay.js: 自サイトのフォームでカード入力）→ **v2 Checkout Session（PAY.JPがカード入力画面をホスト）** | カード情報が一切自サイトを通過しない。PCI DSSのスコープが最小化されセキュリティリスクを大幅に軽減 |
| キャンセルURL対応 | `cancelCallback`（`/transactions/{transaction}/cancel`）を実装 | PAY.JPのカード入力ページでキャンセルした際に `pending_payment` が孤立するバグを防ぐため |
| 孤立トランザクション対策 | 購入再試行時に同一商品・同一ユーザーの `pending_payment` を自動キャンセル | セッション期限切れ（410エラー）等で残った未決済トランザクションを自動クリアするため |
| 購入レートリミット | `throttle:5,60`（60分間最大5回）を `transactions.store` に適用 | クレジットマスター攻撃（他人のカードで少額テスト決済を繰り返す手口）への対策 |

### 画像アップロード: AJAXプリアップロード方式の採用
| 項目 | 決定内容 | 理由 |
|---|---|---|
| アップロード方式 | ファイル選択時に即時AJAX送信 → `temp/lures/` に保存 → フォーム確定時に `lures/` へ移動 | HTMLの `<input type="file">` はページリロードでクリアされるため、バリデーションエラー時に画像を再選択させるUXを回避 |
| 復元方法 | `old('temp_image_paths')` でサーバー側の一時パスを引き継ぐ | リダイレクト後もBladeで `existingPaths` として渡し、Alpine.jsがプレビューを復元 |
| パストラバーサル対策 | `temp_image_paths.*` / `temp_video_path` にRegex検証 + `Storage::exists()` チェック | 任意パスを本番ディレクトリへ移動する攻撃を防ぐ |
| サイズチェック | ファイル選択時にJavaScript（Alpine.js `addFiles()`内）で即時5MBチェック | フォーム送信前にUX的に早期フィードバックを提供するため |

### レンジ（range）: 複数選択対応
| 項目 | 決定内容 | 理由 |
|---|---|---|
| DB設計 | 既存の `range` enumカラムはそのままに、新たに `ranges` JSON型カラム（nullable）を追加 | MySQLのenum変更マイグレーションが複雑な上、SQLiteテスト環境では `MODIFY COLUMN` が非サポート。JSON型なら複数値を柔軟に格納できる |
| UI | ラジオボタン（単一選択）→ チェックボックス（複数選択）に変更 | ルアーが複数のレンジで使われるユースケースへの対応 |
| バリデーション | `ranges.*` を StoreLureRequest / UpdateLureRequest で検証 | `buildLureData()` の `safe()->except()` リストからも除外して二重送信を防ぐ |

## 2026-11-13

### 取引ID: ランダム英数字コード（order_number）の採用
| 項目 | 決定内容 | 理由 |
|---|---|---|
| ID形式 | 数値の主キー（`id`）とは別に `order_number`（10桁英数字）を追加 | 連番IDでは取引量が外部から推測可能。ランダムコードにすることで情報漏洩リスクを低減 |
| 文字セット | A-Z（I・O除く）＋ 2-9（0・1除く）の32文字 | 視認性の低い文字（I/1、O/0）を除外してサポート対応時の読み間違いを防ぐ |
| 重複対策 | do-while ループで事前チェック ＋ DBのUNIQUE制約で二重保護 | 32^10 ≒ 1京通りのため実用上衝突しないが、安全のため両層で保護 |
| URL変更 | `getRouteKeyName()` で `/transactions/{id}` → `/transactions/{order_number}` に変更 | ユーザーに見えるURLにも意味のないIDを使わない |

### 売上残高・販売実績の加算タイミング変更
| 変更前 | 変更後 | 理由 |
|---|---|---|
| `paid`（支払い完了）時に加算 | `completed`（取引完了）時に加算 | 商品が届いて取引が確定するまでは売上が確定していないため。またキャンセル時のデクリメント処理が不要になりシンプルになる |
